## 0. Кратко для заказчика

SecretPiece — кроссплатформенный Rust-инструмент для создания **зашифрованного скрытого хранилища внутри обычного файла на флешке**. Приложение не размечает диск, не меняет таблицу разделов, не форматирует носитель и не устанавливает драйверы. Оно работает только с обычными файлами, поэтому структура флешки и уже лежащие на ней данные остаются нетронутыми.

Внутри хранилища можно удобно хранить, импортировать и экспортировать файлы, шифровать их, делать версии и снапшоты, безопасно удалять и затирать, а также создавать **скрытый том**, который открывается отдельным паролем и не виден при открытии внешнего тома.

Ключевая идея названия: **Secret Piece** — «кусок секрета». Это одновременно:

- зашифрованные чанки (pieces) данных;
- схема разделения секрета Шамира для восстановления доступа;
- скрытый «кусок» флешки, который выглядит как обычный файл.

### 0.1. Что делаем сейчас

1. Проверили название на коллизии.
2. Подготовили это ТЗ: архитектура, криптография, формат контейнера, UX, кроссплатформенность, безопасность, тесты, дорожная карта.
3. После согласования ТЗ — создаём репозиторий, каркас проекта и первый рабочий прототип.
4. Публикация на GitHub — после получения имени пользователя и токена/доступа.

### 0.2. Что принципиально не делаем в v1

- Не создаём настоящие скрытые разделы и не правим MBR/GPT.
- Не форматируем флешку и не меняем её файловую систему.
- Не устанавливаем драйверы и не требуем администраторских прав для основных сценариев.
- Не обещаем «физически гарантированное» уничтожение данных на SSD/флешках: из-за wear leveling и контроллера это невозможно гарантировать только перезаписью. Обеспечиваем лучший достижимый уровень и честно документируем ограничения.
- Не делаем «невидимый раздел», который невозможно обнаружить. Содержимое скрытого тома неотличимо от случайных данных без пароля, но само наличие контейнерного файла скрыть нельзя. Это важно проговорить до начала разработки.

### 0.3. Главный компромисс

Есть два подхода:

1. **Настоящий скрытый раздел** — красиво звучит, но ломает структуру носителя, требует прав администратора, по-разному работает на FAT32/exFAT/NTFS/APFS/ext4 и почти гарантированно создаёт проблемы с кроссплатформенностью.
2. **Скрытый том внутри обычного файла** — файл лежит на флешке как обычный файл, внутри него зашифрованный виртуальный диск, а внутри виртуального диска — ещё один скрытый том. Структура флешки не меняется, работает везде, где есть обычная файловая система.

Выбираем второй подход. Это не компромисс «чуть хуже», а более надёжное и переносимое решение для заявленной задачи.

## 2. Цели, не-цели и принципы

### 2.1. Цели v1.0

1. **Безопасное хранилище на флешке**: контейнерный файл, который можно потерять, но нельзя прочитать без пароля.
2. **Скрытый том**: второй, независимый том внутри того же файла, открываемый отдельным паролем.
3. **Удобное управление файлами**: импорт, экспорт, переименование, перемещение, поиск, версии, корзина.
4. **Безопасное удаление**: затирание файлов, свободного места и контейнера с понятными отчётами.
5. **Кроссплатформенность**: Windows 10/11, macOS 13+, Linux (Ubuntu 22.04+, Fedora, Arch), без администраторских прав для базовых сценариев.
6. **Прозрачность**: открытый исходный код, воспроизводимые сборки, отсутствие телеметрии и сетевых вызовов.
7. **Восстанавливаемость**: резервные заголовки, снапшоты, `doctor`, восстановление по схеме Шамира.

### 2.2. Не-цели v1.0

- Защита от вредоносного ПО, кейлоггеров, компрометации ОС и холодной загрузки.
- Защита от принуждения (rubber-hose) и юридического давления.
- Полное сокрытие факта наличия контейнера на носителе.
- Гарантированное физическое уничтожение данных на SSD/флешках.
- Монтирование как буквы диска через драйвер (WinFsp/FUSE) — только в v2, опционально.
- Мобильные приложения — после v1.0.
- Облачная синхронизация «из коробки» — контейнер можно синхронизировать любым облаком, но конфликты решаются вручную.

### 2.3. Принципы

1. **Не ломать носитель.** Только обычные файлы и штатные операции ОС. Никаких изменений таблицы разделов, загрузочных секторов и файловой системы.
2. **Не изобретать криптографию.** Только стандартные примитивы и проверенные crate-ы.
3. **Безопасность по умолчанию.** Шифрование, AEAD, Argon2id, атомарные коммиты, read-only при сомнениях.
4. **Честность.** В документации прямо написано, что защищает, а что нет.
5. **Кроссплатформенность через простые абстракции.** Ядро не знает про Windows/macOS/Linux; платформенный слой — тонкий.
6. **Данные важнее скорости.** Лучше медленнее, но с fsync и восстановлением.
7. **Никакой телеметрии.** Приложение не делает сетевых запросов, кроме опциональной проверки обновлений (по умолчанию выключена).

## 3. Пользователи и сценарии

### 3.1. Персоны

| Персона | Задача | Критично |
|---|---|---|
| Обычный пользователь | держать личные документы и фото на флешке, чтобы при потере никто не прочитал | простота, 3 клика, понятные предупреждения |
| IT-специалист | носить рабочие секреты, ключи, бэкапы | CLI, скрипты, надёжность, аудит |
| Путешественник | скрытый том на флешке, внешний том-приманка | скрытность, отсутствие следов, работа без админа |
| Небольшая команда | общий контейнер с доступом по ключам получателей | слоты получателей, Shamir, версии |
| Исследователь безопасности | проверить формат, воспроизвести сборку | открытый код, тест-векторы, документация |

### 3.2. Ключевые сценарии

**S1. Создать хранилище на флешке.**
Пользователь вставляет флешку, запускает SecretPiece, выбирает «Создать хранилище», указывает размер, пароль, профиль сохранности. Приложение создаёт один файл `personal.spv` (или набор частей на FAT32). Существующие файлы не меняются. Админские права не нужны.

**S2. Открыть и поработать.**
Пользователь открывает контейнер, вводит пароль, видит файловый менеджер, перетаскивает файлы, переименовывает, ищет, экспортирует. При бездействии хранилище блокируется.

**S3. Скрытый том.**
Пользователь создаёт внешний том с «обычными» файлами и скрытый том с настоящими. При вводе пароля внешнего тома открывается только внешний. При вводе пароля скрытого — только скрытый. Внешний том по умолчанию открывается read-only, чтобы случайно не затереть скрытый.

**S4. Потеря флешки.**
Посторонний видит файл `personal.spv` (или несколько частей), не может определить содержимое, не может открыть без пароля. Все метаданные и имена файлов зашифрованы.

**S5. Безопасное удаление.**
Пользователь удаляет файл с затиранием, затем затирает свободное место контейнера. Получает отчёт: сколько байт перезаписано, сколько проходов, что проверено, какие ограничения.

**S6. Восстановление доступа.**
Пароль забыт, но есть recovery key или K из N долей Шамира. Пользователь восстанавливает доступ и задаёт новый пароль.

**S7. Командная работа.**
Владелец добавляет получателей по их публичным ключам X25519. Каждый открывает контейнер своим приватным ключом, не зная общего пароля.

**S8. Повреждение.**
Флешку выдернули во время записи. При следующем открытии `doctor` находит незавершённую транзакцию, откатывается к последнему коммиту, сохраняет целостность.

## 4. Термины

| Термин | Значение |
|---|---|
| **Контейнер** | обычный файл (или набор частей), внутри которого лежит зашифрованное хранилище |
| **Том** | логическое хранилище внутри контейнера: внешний или скрытый |
| **Скрытый том** | независимый том, занимающий область, которая для внешнего тома выглядит как свободное место |
| **Слот ключа** | запись в заголовке, позволяющая разблокировать мастер-ключ: пароль, recovery, FIDO2, X25519-получатель |
| **Мастер-ключ** | случайные 32 байта, корень ключевой иерархии тома |
| **Ключ файла** | случайный ключ, которым шифруются чанки конкретного файла; удаление ключа = crypto-shred |
| **Чанк** | блок данных фиксированного размера, единица шифрования и произвольного доступа |
| **Суперблок** | атомарная запись с корнем метаданных и номером поколения |
| **Снапшот** | зафиксированное состояние индекса на момент времени |
| **Профиль сохранности** | набор правил: версии, корзина, журнал, реплики, проверки |
| **Затирание** | перезапись данных случайными байтами; на флешках не гарантирует физическое уничтожение |
| **Crypto-erase** | уничтожение ключей, после которого шифротекст бесполезен |
| **Deniable mode** | режим, в котором внешний том не знает о скрытом и по умолчанию read-only |
| **Protected mode** | режим, в котором внешний том резервирует область скрытого тома (безопаснее, но факт резервирования виден при знании пароля внешнего тома) |

## 5. Модель угроз

### 5.1. Активы

- Содержимое файлов.
- Имена файлов, структура папок, размеры, время изменения.
- Пароли, ключи, recovery-коды, доли Шамира.
- Сам факт существования скрытого тома (частично).
- Целостность контейнера.

### 5.2. Противники

| Противник | Возможности | Защита |
|---|---|---|
| Случайный находчик | нашёл флешку, просматривает файлы | шифрование, отсутствие явных имён |
| Любопытный коллега | получил краткий доступ к разблокированному ПК | auto-lock, скрытие окон, очистка буфера |
| Офлайн-атакующий с копией контейнера | перебирает пароли, анализирует формат | Argon2id, AEAD, отсутствие оракулов |
| Криминалистика | снимает образ носителя, ищет артефакты | шифрование, скрытый том, затирание, crypto-erase |
| Вредоносное ПО | кейлоггер, дамп памяти, доступ к файлам | **не защищаем** (вне модели) |
| Принуждение | требует пароль | **не защищаем**; скрытый том может помочь, но это не гарантия |
| Злоумышленник с физическим доступом к железу | аппаратный кейлоггер, evil maid | **не защищаем** без проверки подписей и доверенной загрузки |
| Атакующий, откатывающий контейнер | подменяет файл старой копией | частично: поколения, предупреждение; полноценный anti-rollback требует внешнего якоря |

### 5.3. Что защищаем

- Конфиденциальность данных при потере/краже носителя.
- Конфиденциальность имён и структуры каталогов.
- Целостность данных и метаданных (AEAD, хеши, суперблоки).
- Содержимое скрытого тома и его ключевой материал неотличимы от случайных данных без пароля (факт наличия контейнера скрыть нельзя).
- Устойчивость к обрыву питания и извлечению носителя.
- Отсутствие открытого текста на диске и в логах.

### 5.4. Что не защищаем

- Разблокированное устройство и запущенный процесс.
- Кейлоггеры, перехват ввода, дампы памяти, cold boot.
- Компрометацию ОС, драйверов, прошивки флешки.
- Аппаратные закладки и злонамеренный контроллер USB.
- Принуждение к выдаче пароля.
- Полное сокрытие факта наличия контейнера.
- Гарантированное физическое уничтожение данных на flash/SSD.
- Защиту от копирования контейнера до уничтожения.
- Сетевые атаки: приложение не работает по сети.

### 5.5. Допущения

- ОС и crypto-библиотеки не скомпрометированы.
- Источник случайности ОС (`getrandom`) корректен.
- Пользователь выбирает достаточно стойкий пароль.
- Пользователь хранит recovery-коды отдельно от контейнера.
- Часы системы могут быть неверны; время не используется для безопасности.
- Флешка может быть отформатирована в FAT32, exFAT, NTFS, APFS, ext4; на FAT32 действует ограничение 4 ГиБ на файл.

## 6. Продукт: режимы хранения и профили сохранности

### 6.1. Режимы хранения («уровни»)

Пользователь выбирает режим при создании хранилища. Все режимы, кроме sharded, используют один и тот же формат контейнера; отличается только раскладка и политика.

| Уровень | Название | Что создаётся | Скрытность | Безопасность | Когда использовать |
|---|---|---|---|---|---|
| L1 | **Sealed file** | один файл `*.spv` | низкая: видно, что файл зашифрован | высокая | бэкапы, облако, передача |
| L2 | **Vault folder** | папка с зашифрованными blobs + индекс | низкая | высокая | синхронизация, очень большие объёмы |
| L3 | **Hidden volume** | внешний том + скрытый том в конце файла | средняя | средняя/высокая | флешка, «внешний» и «настоящий» тома |
| L4 | **Nested vault** | контейнер внутри внешнего тома | средняя | высокая | когда не нужен overlap свободного места |
| L5 | **Sharded vault** | k/n erasure-coded частей на разных носителях | нет | очень высокая | disaster recovery, раздельное хранение |
| L6 | **Paranoid** | L3 или L5 + снапшоты + 2FA + реплики | средняя | максимальная | особо ценные данные |

**L1. Sealed file.** Классический контейнер. Все данные, метаданные и ключи — внутри. Удобно копировать, синхронизировать, отправлять. Скрытности нет: расширение и размер выдают назначение. Можно переименовать в `family_photos.7z`, но это слабая маскировка.

**L2. Vault folder.** В папке лежат файлы-блоки с случайными именами и один зашифрованный индекс. Плюс: можно синхронизировать отдельные блоки, удобно для очень больших хранилищ и облаков с лимитами. Минус: структура папки видна, количество файлов и их размеры утекают.

**L3. Hidden volume.** Основной режим для флешки. Внешний том выглядит как обычный контейнер с «несекретными» файлами. Внутри него, в области, которая для внешнего тома является свободным местом, лежит скрытый том. Пароль внешнего тома открывает только внешний. Пароль скрытого — только скрытый. Внешний том по умолчанию read-only, чтобы не затереть скрытый.

**L4. Nested vault.** Внутри внешнего тома лежит файл-контейнер. Внешний том видит его как файл со случайными байтами. Плюс: невозможно случайно затереть скрытые данные внешними операциями. Минус: сам факт наличия большого случайного файла виден при открытом внешнем томе.

**L5. Sharded vault.** Контейнер кодируется Reed-Solomon в n частей, восстанавливается по любым k. Части можно хранить на разных флешках, в разных местах, у разных людей. Минус: сложнее UX, каждая часть имеет заголовок и выдаёт своё назначение.

**L6. Paranoid.** Комбинация: скрытый том + снапшоты + recovery + FIDO2/ключ-файл + реплика на втором носителе + проверка чтения после записи. Для параноиков и особо важных данных.

### 6.2. Профили сохранности («уровни сохранения»)

Профиль определяет, сколько версий, копий и проверок делает приложение. Его можно менять после создания (кроме параметров, влияющих на формат).

| Профиль | Версии | Корзина | Журнал | Реплики | Проверка записи | Auto-lock |
|---|---|---|---|---|---|---|
| **Fast** | нет | нет | нет | нет | нет | 5 мин |
| **Balanced** (по умолчанию) | 7 дней / 10 версий | 30 дней | да | нет | да | 3 мин |
| **Paranoid** | 30 дней / 50 версий | 90 дней | да | 1 копия | да, с чтением | 1 мин |
| **Custom** | вручную | вручную | вручную | вручную | вручную | вручную |

Важно: профиль не меняет криптографию и формат. Это политика поверх ядра. Даже в Fast коммиты атомарны и защищены AEAD.

### 7.3. Потоки данных

**Создание контейнера**

1. Проверить носитель, ФС, свободное место, права.
2. Сгенерировать мастер-ключ, recovery key, соль, UUID.
3. Создать файл, заполнить случайными данными (preallocate) или зарезервировать место.
4. Записать заголовок A + backup, (опционально) скрытый заголовок B + backup.
5. Записать суперблоки и пустой индекс.
6. `fsync`, проверить чтением заголовков.
7. Показать recovery-код и попросить сохранить.

**Импорт файла**

1. Открыть исходный файл, определить размер.
2. Сгенерировать ключ файла и nonce-prefix.
3. Нарезать на чанки, зашифровать, записать в свободные чанки.
4. `fsync` данных.
5. Обновить индекс (COW), записать новые метаданные.
6. `fsync`, записать суперблок с новым поколением.
7. Освободить старые чанки после успешного коммита.

**Экспорт**

1. Найти файл в индексе.
2. Прочитать extents, расшифровать чанки потоково.
3. Записать в целевой файл, `fsync`, сверить BLAKE3.
4. Не держать весь файл в памяти.

**Блокировка**

1. Занулить мастер-ключ, ключи файлов, буферы.
2. Закрыть дескрипторы, снять блокировки.
3. Очистить буфер обмена и превью.
4. Вернуть UI в состояние «заблокировано».

### 7.4. Выбор GUI

Предварительное решение: **Tauri 2 + Svelte 5 + TypeScript**, ядро на Rust.

Почему:

- нативный WebView вместо Electron: размер 10–25 МБ;
- хороший UX для файлового менеджера: таблицы, drag-and-drop, контекстные меню;
- кроссплатформенность Windows/macOS/Linux;
- Rust-бэкенд напрямую вызывает `sp-vault`, без сетевого слоя;
- легко сделать красивый интерфейс и локализацию.

Минусы:

- WebView2 на Windows (обычно уже установлен), WebKitGTK на Linux (зависимость);
- два языка (Rust + TS) и два набора тестов;
- sandbox/portal в Flatpak может ограничивать доступ к флешкам.

Альтернатива: **egui/iced** — полностью Rust, проще сборка, но слабее UX и доступность. Оставляем как запасной вариант, если Tauri создаст проблемы с поставкой. Решение фиксируем после прототипа (ADR-0002).

## 8. Криптография

### 8.1. Примитивы

| Функция | Алгоритм | Параметры v1 |
|---|---|---|
| CSPRNG | `getrandom` (ОС) | 32 байта на ключ |
| KDF пароля | Argon2id (RFC 9106) | 512 МиБ, t=3, p=4 (default); 256 МиБ — light; 1 ГиБ, t=4 — paranoid |
| AEAD | XChaCha20-Poly1305 | 256-битный ключ, 192-битный nonce, 128-битный tag |
| HKDF | HKDF-SHA256 | доменное разделение по строкам |
| Хеш | BLAKE3 | 256 бит; keyed mode для MAC |
| Обмен ключами | X25519 (RFC 7748) | эфемерный ключ на сообщение |
| Подписи | Ed25519 | только для манифестов обновлений/релизов, не для томов |
| Shamir | GF(256), `sharks` | K из N, N ≤ 255 |
| Кодирование recovery | BIP39 (24 слова) + Bech32m | 256 бит энтропии |
| Сравнение | `subtle` | constant-time |
| Затирание памяти | `zeroize` + `secrecy` | при drop и блокировке |

Запрещено:

- собственные шифры, режимы, KDF, протоколы;
- ECB, CBC без MAC, SHA-1/MD5, RSA с самодельным padding;
- пароли в argv, логах, конфигах;
- «обфускация вместо шифрования».

### 8.2. Иерархия ключей

```
Пароль + keyfile + FIDO2
          │
          ▼
   KEK слота (Argon2id/HKDF)
          │  unwrap
          ▼
   Master key (32 B, random)
          │
   ┌──────┼─────────────────────────────┐
   │      │                             │
   ▼      ▼                             ▼
Metadata  File keys (32 B на файл)   Hidden master key
key       │                             │
          ▼                             ▼
     Chunk key = HKDF(FK, file_id, "chunk")
          │
          ▼
     XChaCha20-Poly1305
```

- **Master key** генерируется CSPRNG при создании, никогда не меняется (кроме явного rekey).
- **Header key** = HKDF(master, salt=header_area_id, info="SPV1 header") — расшифровывает служебный payload заголовка (версия, UUID, флаги).
- **Metadata key** = HKDF(master, salt=volume_uuid, info="SPV1 metadata").
- **File key** — случайные 32 байта на файл/версию; хранится внутри зашифрованных метаданных.
- **Chunk key** = HKDF(file_key, salt=file_id, info="SPV1 chunk").
- **Hidden master key** — независимый мастер-ключ скрытого тома.
- **Recovery key** — 32 случайных байта, кодируются в 24 слова BIP39; слот восстанавливает master.
- **Shamir** — доли от master key; K из N восстанавливают master.
- **Recipient slot** — master заворачивается в X25519-ECDH с публичным ключом получателя.

### 8.3. Слоты ключей и разблокировка

В заголовке 8 фиксированных слотов. Тип слота определяется его позицией и **не хранится в открытом виде**. Каждый слот заворачивает один и тот же master key своим KEK. Служебный payload заголовка шифруется header key, выведенным из master.

| Индекс | Назначение | Что нужно | KDF |
|---|---|---|---|
| 0 | Основной пароль | пароль (+ keyfile) | Argon2id |
| 1 | Второй пароль (опционально) | пароль (+ keyfile) | Argon2id |
| 2 | Recovery | 24 слова / QR | HKDF (высокая энтропия) |
| 3 | FIDO2 | токен + PIN | hmac-secret + HKDF |
| 4–7 | Получатели | приватный ключ X25519 | ECDH + HKDF |

- Пустой слот заполнен случайными байтами; отличить его от используемого без ключа нельзя.
- Парольные слоты 0 и 1 — максимум два; каждый добавляет ~1 секунду к попытке.
- Recovery/FIDO2/получатели не используют Argon2, поэтому дешёвы.
- Shamir не занимает слот: доли восстанавливают master напрямую, после чего создаётся новый парольный слот.

Порядок разблокировки:

1. Прочитать заголовок A. Если повреждён/не читается — backup A′.
2. В зависимости от выбранного метода попробовать соответствующие слоты:
   - пароль → слоты 0 и 1;
   - recovery → слот 2;
   - FIDO2 → слот 3;
   - получатель → слоты 4–7.
3. Развернуть master, вывести header key, расшифровать payload, проверить версию и UUID.
4. Если не вышло и включён автопоиск — попробовать заголовок B/B′ (скрытый том).
5. При ошибке вернуть один и тот же код `E_UNLOCK`, без указания, какой слот/заголовок был близок.
6. При успехе — загрузить суперблок, проверить MAC, загрузить индекс.

Важно: при неверном пароле и при повреждённом заголовке сообщение одинаковое. При явном выборе «внешний/скрытый» время не зависит от существования другого тома. При автопоиске приложение пытается оба заголовка; это осознанный компромисс между UX и временем.

Header payload (шифруется header key):

| Поле | Размер |
|---|---|
| `format_version` | 4 |
| `algorithm_id` | 4 |
| `header_size` | 4 |
| `volume_uuid` | 16 |
| `created_at_ms` | 8 |
| `flags` | 2 |
| `header_generation` | 4 |
| reserved | до 61 КиБ |
| padding | random |

- Payload шифруется XChaCha20-Poly1305; nonce хранится в открытой части заголовка (24 случайных байта).
- AAD payload = `b"SPV1 header" || header_area_id`.
- AAD слота = `b"SPV1 slot" || header_area_id || slot_index`.
- `header_area_id`: 0 = outer A, 1 = outer A′, 2 = hidden B, 3 = hidden B′.
- Без пароля/ключа слоты и payload неотличимы от случайных данных; в открытом виде остаются только соль, nonce, параметры KDF и позиции.

### 8.4. Шифрование данных

- Размер чанка: **64 КиБ открытого текста**, 64 КиБ + 16 байт тега на диске.
- Nonce (24 байта): `random_prefix[8] || chunk_id_be[8] || zeros[8]`.
  - `random_prefix` уникален для файла/версии и хранится в зашифрованном индексе;
  - `chunk_id` — физический ID чанка, уникальный в томе;
  - уникальность nonce гарантирована парой (prefix, chunk_id).
- AAD: `b"SPV1" || volume_uuid || file_id || version_id || chunk_id || flags`.
- Каждый чанк аутентифицирован отдельно; подмена/перестановка обнаруживается.
- Метаданные шифруются отдельным ключом; nonce — `meta_prefix[8] || block_index[8] || zeros[8]`.
- Слоты и payload заголовка — XChaCha20-Poly1305 с случайным nonce; AAD включает `header_area_id` и индекс слота, без открытого UUID.

Почему XChaCha20-Poly1305:

- 192-битный nonce снижает риск повторного использования;
- постоянное время на всех платформах без AES-NI;
- хорошая скорость (сотни МБ/с на ядро, параллелится по чанкам);
- хорошо изучен, есть RustCrypto-реализация.

AES-256-GCM можно добавить как альтернативный backend позже (algorithm ID в заголовке).

### 8.5. Целостность, версии, anti-rollback

- Каждый чанк — AEAD.
- Метаданные — AEAD + корневой хеш BLAKE3 в суперблоке.
- Суперблок — два экземпляра (A/B) с номером поколения; выбирается валидный с максимальным поколением.
- Заголовки — основной + резервный; при повреждении используется резервный.
- MAC суперблока — keyed BLAKE3 с metadata key.
- **Anti-rollback**: полноценно требует внешнего доверенного состояния (отдельный файл-якорь, TPM, сервер). В v1 — предупреждение, если поколение меньше последнего известного в локальном конфиге; опционально внешний якорь в v2. Не обещаем защиту от копии всего контейнера.
- **Truncation**: суперблок содержит общий размер данных и количество чанков; усечение обнаруживается.
- **Swap/splice**: AAD привязывает чанк к файлу, версии и индексу; перестановка не пройдёт.

### 8.6. Recovery и Shamir

- Recovery key — 32 случайных байта, 24 слова BIP39 (256 бит + checksum). Показывается один раз при создании, повторно — после ввода пароля.
- Recovery-слот хранит master, завёрнутый ключом HKDF(recovery_key). Argon2 не нужен: энтропия 256 бит.
- Shamir: master key делится на N долей, порог K. Доли кодируются в текст с контрольной суммой и ID набора. Восстановление: собрать K долей → master → создать новый парольный слот.
- Смена пароля не меняет master, поэтому доли и recovery остаются валидными.
- Явный rekey (смена master) инвалидирует старые recovery/доли; приложение предупреждает и предлагает пересоздать.

**Формат доли:**

```
SP-SHARE-1
set: <16 hex>
index: <n>/<N>
threshold: <K>
data: <base32>
checksum: <8 hex>
```

Доли можно печатать, сохранять в QR, хранить у разных людей. Приложение не отправляет их никуда.

### 8.7. Слоты получателей X25519

- У получателя есть ключевая пара X25519. Публичный ключ передаётся владельцу.
- Владелец при добавлении получателя:
  1. генерирует эфемерную пару;
  2. считает `shared = X25519(ephemeral_sk, recipient_pk)`;
  3. `KEK = HKDF(shared, salt=ephemeral_pub || recipient_pk, info="SPV1 recipient")`;
  4. заворачивает master в AEAD;
  5. сохраняет `ephemeral_pub`, nonce, ciphertext, fingerprint получателя.
- Получатель открывает том своим приватным ключом; пароль владельца не нужен.
- Приватные ключи хранятся в файле с правами 0600 или в OS keychain (v1.1).
- Отзыв получателя: удалить слот и сделать rekey (иначе старый получатель может открыть старую копию).

### 8.8. Память и побочные каналы

- Все ключи и пароли — в `SecretBox`/`SecretVec`, `zeroize` при drop.
- `mlock`/`VirtualLock` для мастер-ключа и ключей файлов (best-effort; если не удалось — предупреждение в лог, без секретов).
- Запрет core dump: `setrlimit(RLIMIT_CORE, 0)` на Unix, `prctl(PR_SET_DUMPABLE, 0)` на Linux; на Windows — best-effort, документируем.
- Не логировать пути, имена, размеры, пароли, ключи. В логах — только коды операций и счётчики.
- Не использовать `Debug` для структур с секретами; `#[derive(Debug)]` запрещён для `MasterKey`, `FileKey`, `Password`.
- Буферы расшифровки зануляются после использования; превью — в памяти, без кэша на диск.
- Размеры файлов утекают, если не включён padding. Профиль `paranoid` включает фиксированные чанки и случайный padding; `compact` — переменные чанки и сжатие.
- Доступ к файлам внутри контейнера не скрывает паттерны чтения от процесса с правами пользователя; это вне модели.
- Constant-time сравнение тегов — внутри AEAD; свои сравнения — только `subtle`.

### 8.9. Крипто-гибкость и миграция

- В заголовке есть `format_version` и `algorithm_id`.
- Новые алгоритмы добавляются без изменения старых томов; миграция — отдельной командой `sp migrate`.
- Запрещено молча менять параметры Argon2 при открытии: используются параметры, записанные в слоте.
- Ограничения на параметры KDF при чтении: m ≤ 4 ГиБ, t ≤ 10, p ≤ 16 — защита от DoS-заголовков.
- Тест-векторы для Argon2id, XChaCha20-Poly1305, HKDF, X25519, BLAKE3, Shamir — в `sp-crypto/tests/vectors`.

## 9. Формат контейнера SPV1

### 9.1. Физическая раскладка

Контейнер — обычный файл (или набор частей). Внутри него байты располагаются так:

| Смещение | Размер | Назначение |
|---|---|---|
| `0x00000` | 64 КиБ | Заголовок внешнего тома A |
| `0x10000` | 64 КиБ | Резервный заголовок внешнего тома A′ |
| `0x20000` | 64 КиБ | Заголовок скрытого тома B |
| `0x30000` | 64 КиБ | Резервный заголовок скрытого тома B′ |
| `0x40000` | 64 КиБ | Суперблок внешнего тома A |
| `0x50000` | 64 КиБ | Суперблок внешнего тома B |
| `0x60000` | … | Чанки данных/метаданных внешнего тома |
| `N − hidden_size` | hidden_size | Область скрытого тома (в deniable-режиме перекрывается свободным местом внешнего) |

- `N` — полный размер контейнера, кратный 4 КиБ.
- Заголовки и суперблоки имеют фиксированные позиции; это упрощает восстановление.
- Область `0x20000–0x3FFFF` при отсутствии скрытого тома заполнена случайными байтами и неотличима от заголовков.
- Скрытый том хранит свои суперблоки и чанки внутри своей области.
- В **protected mode** внешний суперблок/индекс помечают область скрытого тома как занятую; в **deniable mode** — нет, и внешний том по умолчанию read-only.

### 9.2. Заголовок тома (64 КиБ)

Заголовок выглядит случайным: в открытом виде только слоты (соль, параметры KDF, nonce) и nonce payload. Версия, UUID, флаги и generation находятся внутри зашифрованного payload. Без ключа нельзя отличить используемый заголовок от неиспользуемого.

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 4096 | 8 слотов по 512 байт |
| 4096 | 24 | `payload_nonce` |
| 4120 | 61416 | `payload_ciphertext` (61400 байт открытого текста + 16 тега) |

Payload (открытый текст до шифрования):

| Поле | Размер |
|---|---|
| `format_version` | 4 |
| `algorithm_id` | 4 |
| `header_size` | 4 |
| `volume_uuid` | 16 |
| `created_at_ms` | 8 |
| `flags` (hidden/deniable/protected) | 2 |
| `header_generation` | 4 |
| reserved | до 61 КиБ |
| padding | random |

- `header_key = HKDF(master, salt=header_area_id, info="SPV1 header")`.
- Payload шифруется XChaCha20-Poly1305; AAD = `b"SPV1 header" || header_area_id`.
- `header_area_id`: 0 = outer A, 1 = outer A′, 2 = hidden B, 3 = hidden B′.
- Заголовки A и A′ содержат одинаковый payload, но шифруются с разными nonce/AAD; при открытии выбирается валидный с максимальной generation.
- Заголовки B/B′ — та же структура. Если скрытого тома нет, вся область `0x20000–0x3FFFF` заполнена случайными байтами; отличить её от используемых заголовков без ключа нельзя.
- Открытые поля (позиции, соли, параметры KDF, nonce) не раскрывают содержимое и не доказывают наличие скрытого тома.

### 9.3. Слот ключа (512 байт)

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 32 | `salt` |
| 32 | 1 | `kdf_profile` (0 light, 1 default, 2 paranoid, 3 custom) |
| 33 | 1 | `flags` |
| 34 | 2 | reserved |
| 36 | 4 | `m_cost_kib` |
| 40 | 4 | `t_cost` |
| 44 | 4 | `p_cost` |
| 48 | 24 | `nonce` |
| 72 | 48 | `wrapped_master` (32 байта шифротекста + 16 тега) |
| 120 | 32 | `public_data` (эфемерный pub / fingerprint / credential hash) |
| 152 | 32 | `label_hash` (BLAKE3 от метки, необязательно) |
| 184 | 328 | reserved (random / credential ID) |

- `wrapped_master` = XChaCha20-Poly1305(KEK, nonce, master_key, AAD).
- AAD = `b"SPV1 slot" || header_area_id || slot_index`.
- Индекс слота задаёт метод: 0/1 — пароль, 2 — recovery, 3 — FIDO2, 4–7 — X25519. Тип в открытом виде не хранится.
- Парольный слот: `KEK = Argon2id(NFKC(password) || 0x00 || keyfile_digest, salt, m, t, p)`.
- `keyfile_digest = BLAKE3("SPV1 keyfile" || file_bytes)`; если keyfile нет — 32 нулевых байта и флаг.
- Recovery: `KEK = HKDF(recovery_key, salt, "SPV1 recovery")`; Argon2 не нужен.
- X25519: `KEK = HKDF(X25519(eph_sk, recipient_pk), eph_pub || recipient_pk, "SPV1 recipient")`.
- FIDO2: `KEK = HKDF(hmac_secret_output, salt, "SPV1 fido2")`.
- `label_hash` позволяет показать «какой это слот» после разблокировки, не раскрывая метку до неё.
- Неиспользуемые слоты заполнены случайными байтами; их `wrapped_master` неотличим от используемого.

### 9.4. Суперблок (64 КиБ)

Суперблок шифруется metadata key; без ключа выглядит случайным.

| Поле | Размер | Описание |
|---|---|---|
| `version` | 4 | версия суперблока |
| `generation` | 8 | монотонное поколение |
| `tx_id` | 16 | случайный ID транзакции |
| `root_hash` | 32 | BLAKE3 корень индекса |
| `meta_chunk_count` | 4 | число чанков метаданных |
| `meta_chunk_ids` | 8 × 4096 (32 КиБ) | ID чанков метаданных (до 256 МиБ) |
| `data_chunk_count` | 8 | общее число чанков данных |
| `free_chunk_count` | 8 | свободные чанки |
| `journal_head` | 8 | указатель журнала (0 = нет) |
| `created_at` | 8 | время коммита |
| `mac` | 32 | keyed BLAKE3 по полям |
| padding | остаток | random |

- Суперблок A и B записываются поочерёдно. На открытии читаются оба, проверяются MAC и root, выбирается валидный с максимальной generation.
- Если оба повреждены — `sp doctor` пытается найти предыдущие копии и восстановить индекс; данные без индекса спасаются частично (`salvage`).
- `meta_chunk_ids` ограничивают метаданные 256 МиБ; при превышении — ошибка с рекомендацией перейти на v2/B-tree.

### 9.5. Чанки

- Чанк открытого текста: 64 КиБ.
- На диске: 64 КиБ шифротекста + 16 байт tag = 65 552 байта.
- ID чанка — 64-битный индекс в области данных тома.
- Смещение = `data_start + chunk_id * 65552`.
- Nonce = `random_prefix[8] || chunk_id_be[8] || zeros[8]`.
- AAD = `b"SPV1" || volume_uuid || file_id || version_id || chunk_id || flags`.
- При `compact`-профиле допускаются переменные чанки (сжатие), длина хранится в индексе; при `balanced`/`paranoid` — фиксированные.
- Последний чанк файла дополняется случайными байтами до 64 КиБ; реальная длина — в индексе. Это скрывает размер с точностью до 64 КиБ.
- Пустые файлы не занимают чанков.
- Sparse-файлы: дырки represented как отсутствующие extents; чтение возвращает нули.

### 9.6. Метаданные и индекс

Индекс — зашифрованный снапшот:

- дерево каталогов;
- записи файлов: id, parent, name, type, size, timestamps, mode;
- ключ файла (32 байта) и nonce-prefix;
- extents: логический диапазон → физические чанки;
- версии и снапшоты;
- ссылки на чанки (refcount);
- корзина;
- теги;
- свободная карта чанков.

Формат сериализации: `postcard` (компактный, версионированный) + zstd (опционально) + шифрование. Снапшот режется на чанки по 64 КиБ, каждый шифруется metadata key, корень — BLAKE3 от (id, hash) листьев. Суперблок хранит список ID и корневой хеш.

**Масштаб v1:** до 1 млн файлов, до 4 ТиБ, метаданные до 256 МиБ. При превышении — понятная ошибка, не деградация.

**Версии:** каждая запись файла хранит массив версий. Версия = `{version_id, size, mtime, extents, file_key, nonce_prefix, parent_version}`. Изменение файла создаёт новую версию; старые чанки не перезаписываются, пока на них есть ссылки. Удаление версии уменьшает refcount; GC освобождает чанки.

**Снапшоты:** именованный снимок корня индекса. Read-only. Можно экспортировать или откатить. Снапшоты удерживают ключи файлов; crypto-shred файла не удаляет данные, пока снапшот существует (приложение предупреждает).

**Свободная карта:** список свободных диапазонов чанков; при аллокации выбирается первый подходящий (first-fit) с выравниванием. Для снижения фрагментации — best-fit для больших файлов. Карта входит в индекс и шифруется.

### 9.7. Атомарность и восстановление после сбоя

Порядок коммита:

1. Записать новые чанки данных в свободные места.
2. `fsync` файла контейнера (Windows `FlushFileBuffers`, macOS `F_FULLFSYNC`).
3. Записать новые чанки метаданных.
4. `fsync`.
5. Записать неактивный суперблок с generation+1 и MAC.
6. `fsync`.
7. Только после этого считать транзакцию завершённой; освободить старые чанки.

Сбой на любом шаге:

- до шага 5 — старый суперблок валиден, новые чанки — мусор, GC их соберёт;
- во время шага 5 — либо старый, либо новый суперблок валиден (запись 64 КиБ не гарантирует атомарность на уровне сектора, поэтому суперблок имеет CRC/MAC и две копии);
- после шага 5 — новый суперблок валиден, старые чанки можно освобождать.

`sp doctor`:

- читает оба суперблока, проверяет MAC/root;
- проверяет достижимость чанков;
- находит orphan-чанки и освобождает их (с подтверждением);
- проверяет заголовки и резервные копии;
- сообщает о потере последнего коммита;
- не «чинит» данные без бэкапа.

Журнал (WAL) в v1 не обязателен для консистентности, но включается в Balanced/Paranoid как лог операций и ускоряет восстановление. Формат журнала — append-only, записи с CRC, ротация после коммита.

### 9.8. Скрытый том

**Раскладка:**

- заголовок B — `0x20000`, backup — `0x30000`;
- данные скрытого тома — `[N − hidden_size, N)`;
- суперблоки скрытого тома — в начале его области;
- чанки — после них;
- внешний том в deniable-режиме считает эту область свободной;
- в protected-режиме внешний индекс помечает её занятой.

**Создание:**

1. Пользователь выбирает внешний размер, размер скрытого, два пароля.
2. Приложение генерирует отдельный master key для скрытого тома.
3. Заполняет контейнер случайными данными (preallocate).
4. Пишет внешний заголовок/суперблок/пустой индекс.
5. Пишет скрытый заголовок B/B′ и суперблоки в конце.
6. Проверяет, что внешний том не пересёк область скрытого (protected) или предупреждает (deniable).

**Открытие:**

- пароль внешнего → внешний том;
- пароль скрытого → скрытый том;
- если пароли совпадают — приложение требует разные (иначе невозможно различить);
- при включённом автопоиске пытаются оба заголовка; при неверном пароле — единая ошибка.

**Режимы:**

- **Deniable (по умолчанию для флешки):** внешний том не знает о скрытом; открывается read-only, пока не передан пароль скрытого или явный `--allow-outer-write`. Запись внешнего может уничтожить скрытый том — предупреждение.
- **Protected:** внешний индекс резервирует область; внешний том можно писать безопасно; но при знании пароля внешнего видно, что часть ёмкости зарезервирована. Это не «доказательство» скрытого тома, но подсказка.

**Честно о скрытности:** содержимое скрытого тома и его ключевой материал неотличимы от случайных данных без пароля. Но сам контейнерный файл, его размер и фиксированные области заголовков видны; по ним нельзя доказать наличие скрытого тома, но можно заподозрить. Мы не обещаем стеганографию и не прячем файл от `ls`. Если нужно спрятать сам факт — используйте обычное имя файла, обложку (например, `family_photos.7z`) и не храните рядом заметки. В v2 — опциональная обложка-контейнер.

### 9.9. FAT32 и разбиение на части

FAT32 не поддерживает файлы > 4 ГиБ. Решение:

- контейнер автоматически режется на части по **3.5 ГиБ** (настраивается, максимум 3.9 ГиБ);
- имена: `vault.spv.000`, `vault.spv.001`, …;
- части — обычные файлы; структура ФС не меняется;
- при открытии приложение сканирует префикс, сортирует части, проверяет непрерывность и собирает логический поток;
- заголовок и скрытый заголовок всегда в части `.000` (смещения < 256 КиБ);
- random access через `part_index = offset / part_size`;
- отсутствующая/лишняя часть — понятная ошибка, без попытки «угадать»;
- `fsync` каждой части после записи;
- на exFAT/NTFS/APFS/ext4 — один файл, если пользователь не включил split вручную.

Проверка ФС:

- Windows: `GetVolumeInformation`;
- macOS: `statfs` (`f_type`);
- Linux: `statfs` + `/proc/mounts`;
- неизвестная ФС — предупреждение и `--split-size` вручную.

### 9.10. Sharded vault (Reed-Solomon)

- Контейнер кодируется в `n` частей, восстанавливается по `k` (например, 3 из 5).
- Части: `vault.spv.shard00` … `shardNN`.
- Заголовок части: magic `SPS1`, version, container_id, k, n, index, shard_size, BLAKE3.
- Части можно хранить на разных носителях; при восстановлении приложение сканирует папку/носители, проверяет ID и собирает.
- Восстановленный контейнер проверяется целиком по BLAKE3 и открывается обычным способом.
- Sharding несовместим с FAT32-сплитом в v1 (каждая часть должна быть < 4 ГиБ; если больше — используйте exFAT/NTFS).
- Sharding не даёт скрытности: заголовок части выдаёт формат.

### 9.11. Версионирование формата

- `format_version` в заголовке; v1 = 1.
- Новые поля добавляются только в конец заголовка/слота или через флаги.
- Чтение старых версий обязательно; запись — только текущая.
- `sp migrate` создаёт новый контейнер и переносит данные; in-place миграция не выполняется (риск потери).
- Формат документируется в `docs/FORMAT.md` с байтовой раскладкой и тест-векторами.

## 10. Виртуальная файловая система

### 10.1. Пути и имена

- Внутренние пути — UTF-8, разделитель `/`.
- Нормализация Unicode NFC; collisions после нормализации запрещены.
- Запрещены: пустые компоненты, `.`/`..`, NUL, `/` внутри имени, имена длиной > 255 байт, путь > 4096 байт.
- Виртуальная ФС **регистрозависима** по умолчанию; UI предупреждает при экспорте на нечувствительную ФС.
- Windows-зарезервированные имена (`CON`, `NUL`, `COM1`…) внутри разрешены, но при экспорте санитизируются.
- Симлинки и хардлинки в v1 не поддерживаются (во избежание escape-атак).
- Права хранятся в метаданных, но на FAT32/exFAT не применяются; при экспорте — best-effort.
- Временные метки — UTC; при экспорте конвертируются в локальное время.

### 10.2. Операции

| Операция | Поведение |
|---|---|
| `import` | потоковое чтение, чанки, коммит; при ошибке — откат |
| `export` | потоковая расшифровка, запись, `fsync`, сверка BLAKE3 |
| `rename` | атомарное обновление индекса |
| `move` | смена parent; без копирования данных |
| `copy` | новые чанки и ключ (или COW-ссылки в рамках одного тома) |
| `delete` | в корзину или сразу; ключ сохраняется, пока есть ссылки |
| `shred` | перезапись чанков + удаление ключа + коммит |
| `mkdir` | запись в индекс |
| `stat` | размер, время, версии, теги |
| `search` | по имени/тегу в расшифрованном индексе; контент — v2 |
| `verify` | чтение и проверка AEAD всех чанков |
| `snapshot` | снимок корня |
| `restore` | откат к снапшоту/версии |

### 10.3. Версии и снапшоты

- При каждом импорте/изменении создаётся версия (если профиль позволяет).
- Версии хранят собственные extents и file key; старые данные не перезаписываются.
- Retention: по времени и количеству; настраивается.
- Снапшот — именованный корень; можно экспортировать целиком или откатить.
- При удалении снапшота refcount уменьшается; GC освобождает чанки.
- Crypto-shred файла при наличии снапшота не удаляет данные; UI предупреждает и предлагает удалить все версии.

### 10.4. Корзина

- Удалённые файлы перемещаются в `/trash` (зашифрованный).
- Retention: 30 дней (Balanced), 90 (Paranoid), 0 (Fast).
- Восстановление с сохранением версии.
- «Очистить корзину» = shred всех файлов.
- Корзина не скрывает факт удаления от того, кто знает пароль.

### 10.5. Квоты и свободное место

- Общая квота тома = размер области данных.
- Предупреждение при 90%, отказ при 100%.
- Резерв 64 МиБ для метаданных и суперблоков.
- Импорт проверяет свободное место до начала; при нехватке — отказ без частичной записи.
- `sp df` показывает занято/свободно/фрагментация.

### 10.6. Ошибки

- `SpError` с кодом, категорией и сообщением без секретов.
- Пользователю — понятный текст и действие («освободите место», «проверьте кабель», «сделайте backup»).
- В лог — код, операция, размер, длительность; без имён файлов и путей.
- Ошибки AEAD → «повреждение или неверный ключ», без деталей.
- При I/O error — переход в read-only, чтобы не усугубить.

## 11. Безопасное удаление и затирание

### 11.1. Что и как затираем

| Объект | Метод | Гарантия |
|---|---|---|
| Файл в томе | перезапись чанков random + удаление file key + коммит | логическая; на flash не физическая |
| Версии/снапшоты | удаление ссылок + перезапись + GC | логическая |
| Свободное место тома | заполнение свободных чанков random + коммит | логическая |
| Контейнер целиком | перезапись заголовков/суперблоков + удаление файла + free-space wipe | логическая + crypto-erase |
| Свободное место флешки | временные файлы random, fsync, чтение-проверка, удаление | логическая, без метаданных ФС |
| Устройство | raw write / NIST 800-88, только explicit | зависит от контроллера |

### 11.2. Проходы

- **Quick** — 1 проход случайными байтами.
- **Balanced** — 3 прохода: random, complement, random.
- **Paranoid** — 7 проходов + чтение-проверка.
- **Crypto-erase** — уничтожение ключей; самый быстрый и надёжный для шифротекста.

Для HDD несколько проходов имеют смысл; для flash/SSD — почти нет из-за wear leveling. Приложение честно пишет это в отчёте.

### 11.3. Затирание файла (shred)

1. Проверить, что файл не открыт и не используется.
2. Определить все версии/снапшоты; если есть — предупредить.
3. Перезаписать каждый чанк случайными байтами (новый nonce не нужен, пишем поверх).
4. `fsync`.
5. Удалить file key из индекса.
6. Записать новый суперблок.
7. Освободить чанки; при `--compact` — перезаписать старые метаданные.
8. Отчёт: байты, проходы, длительность, что не гарантируется.

### 11.4. Затирание свободного места флешки

Команда `sp wipe-free --target E:\`:

1. Проверить, что это не системный диск; требуем явное подтверждение.
2. Определить свободное место; оставить 64 МиБ.
3. Создавать временные файлы `sp-wipe-<random>.tmp` размером до 3.5 ГиБ (FAT32) и заполнять `getrandom`.
4. `fsync` каждого файла.
5. Прочитать обратно и сверить BLAKE3 (логическая проверка).
6. Удалить файл.
7. Повторить N проходов.
8. Отчёт: сколько записано, сколько свободно, проходы, ошибки, ограничения.

Что **не** затирается:

- метаданные файловой системы (FAT, MFT, directory entries);
- журналы ФС;
- bad blocks и переназначенные сектора;
- over-provisioning и кэш контроллера;
- старые копии файлов, сделанные ОС/облаком.

Поэтому free-space wipe — вспомогательная мера, а не гарантия. Для настоящей защиты — шифрование всего диска + crypto-erase.

### 11.5. Уничтожение контейнера

`sp destroy vault.spv`:

1. Требует ввода имени файла/фразы подтверждения.
2. Перезаписывает заголовки A/A′/B/B′ (256 КиБ) случайными данными, `fsync`.
3. Перезаписывает суперблоки и первые/последние 1 МиБ.
4. Удаляет файл(ы) частей.
5. Опционально запускает free-space wipe.
6. Отчёт + предупреждение о копиях и flash.

`crypto-erase` без перезаписи: уничтожить все слоты ключей и мастер-ключ. Если старые копии контейнера существуют, они всё ещё открываются старым паролем — предупреждение.

### 11.6. Затирание устройства (v2, experimental)

- Только по явному `--device` и `--i-understand`.
- Требует размонтирования, эксклюзивной блокировки, прав администратора.
- Windows: `FSCTL_LOCK_VOLUME`, `FSCTL_DISMOUNT_VOLUME`, запись в `\\.\PhysicalDriveN`.
- Linux: `O_DIRECT` на блочное устройство, `BLKFLSBUF`, `fsync`.
- macOS: raw device + `diskutil unmountDisk`.
- Профили: NIST SP 800-88 Clear/Purge, 1/3/7 проходов.
- Для flash рекомендуется crypto-erase, а не многопроходная запись.
- Никогда не выбирать системный диск по умолчанию; проверять модель/серийник и просить подтверждение.

### 12.1. Матрица поддержки

| ОС | Версии | Архитектуры | Формат поставки | Статус |
|---|---|---|---|---|
| Windows | 10 22H2, 11 | x86_64 | portable zip, MSI, (MSIX — later) | v1 |

| macOS | 13 Ventura+ | Intel, Apple Silicon (universal2) | .dmg, .app, notarized | v1 |
| Linux | Ubuntu 22.04+, Fedora 38+, Arch | x86_64 | AppImage, .deb, .rpm, tar.gz | v1 |

| Android | 12+ | arm64 | APK/AAB | после v1 |

Базовые сценарии (создать, открыть, импорт/экспорт, затирание) не требуют администраторских прав. Права нужны только для `device-wipe` и, опционально, для монтирования (v2).

### 12.2. Файловые системы

| ФС | Макс. файл | Поддержка | Особенности |
|---|---|---|---|
| FAT32 | 4 ГиБ | да, auto-split | нет прав, нет длинных имён > 255, нет journal |
| exFAT | 16 ЭиБ | да, рекомендуется | хорош для флешек > 32 ГиБ |
| NTFS | 16 ЭиБ | да | права, journal, Windows |
| APFS | 8 ЭиБ | да | macOS, cloning |
| HFS+ | 8 ЭиБ | да, legacy | deprecated Apple |
| ext4 | 16 ТиБ | да | Linux |
| XFS/Btrfs | большие | да | Linux |
| SMB/NFS | зависит | предупреждение | блокировки и fsync ненадёжны |
| exFAT на Linux | да | зависит от ядра | проверить `fsync` |

Правила:

- На FAT32 — автосплит; на остальных — один файл.
- На сетевых ФС — предупреждение о возможной потере атомарности; рекомендация не использовать для активной записи.
- На read-only носителе — открыть read-only.
- На ФС без поддержки `fsync` — предупреждение, но работаем.

### 12.3. Съёмные носители

- Определение: Windows `DRIVE_REMOVABLE`, macOS `kDiskDescriptionRemovable`, Linux `ID_BUS=usb`.
- При извлечении: auto-lock, закрытие дескрипторов, очистка ключей.
- При повторном подключении: предложить открыть последний том (если включена история; по умолчанию история путей не сохраняется).
- Безопасное извлечение: `sp eject` / кнопка в GUI; вызывает штатный API ОС.
- Если носитель отключён во время записи: операция возвращает `E_IO`, том помечается «грязным», при следующем открытии — `doctor`.
- Не монтировать автоматически; не писать на носитель без явного действия пользователя.

### 12.4. Сборка и поставка

- Rust stable, edition 2024, MSRV 1.85.
- CI собирает на Windows Server 2022, macOS 14, Ubuntu 24.04.
- CLI: статическая сборка (musl) для Linux, MSVC для Windows, universal2 для macOS.
- GUI: Tauri bundler; WebView2 bootstrapper на Windows; WebKitGTK dependency на Linux.
- Portable mode: бинарник + конфиг рядом; не оставляет следов в `%APPDATA%`/`~/.config`, кроме явного конфига.
- Подписи: Windows Authenticode, macOS codesign + notarization, Linux minisign/cosign.
- Воспроизводимость: `--locked`, фиксированный toolchain, `SOURCE_DATE_EPOCH`, remap-path-prefix; проверка хешей двумя сборщиками.

### 12.5. Локализация и доступность

- Языки v1: русский, английский.
- Все строки — в ресурсах, без конкатенации.
- Форматирование размеров/дат — через locale.
- Клавиатурная навигация, focus ring, screen reader labels.
- Контрастность WCAG AA; масштабирование 125–200%.
- Не полагаться только на цвет; ошибки — текстом.
- RTL — после v1.

### 13.4. Пароли и секреты

- Анимации — короткие, отключаемые.

### 14.3. Безопасность в UI

- Auto-lock по бездействию, блокировке экрана, suspend, извлечению носителя.
- Обратный отсчёт до блокировки в статусбаре.
- Очистка буфера обмена через N секунд после копирования секрета.
- Превью — в памяти; миниатюры не кэшируются на диск.
- Защита от скриншотов — best-effort; предупреждение, что на Linux не гарантируется.
- Паника: `Ctrl+Shift+L` — мгновенная блокировка; `Ctrl+Shift+Q` — блокировка и выход.
- Duress-пароль (опционально) открывает **декой-том**, а не стирает данные. Стирание по duress-паролю не делаем: слишком опасно и юридически спорно.
- Пароль не показывается; strength meter — локальный (`zxcvbn`), без сети.
- «Скрытый том» не афишируется на главном экране; открывается через меню/горячую клавишу.

### 14.4. Открытие файлов внешними приложениями

- Малые файлы (изображения, текст, PDF) — предпросмотр в памяти.
- Внешнее приложение: расшифровать во временный файл в защищённой папке, открыть, удалить после закрытия (best-effort), затереть.
- Предупреждение: внешнее приложение может сохранить копию/кэш/thumbnails; это вне контроля SecretPiece.
- Для больших файлов — «Экспортировать» вместо «Открыть».
- Временные файлы: права 0600, случайное имя, удаление при блокировке/выходе; при аварийном завершении — очистка при следующем запуске.

## 15. API и SDK

### 15.1. Rust API

```rust
use secretpiece::{Vault, Unlock, Profile};

let mut vault = Vault::open("E:/vault.spv", Unlock::password("..."))?;
vault.put_file("docs/report.pdf", &mut reader)?;
let mut out = File::create("report.pdf")?;
vault.get_file("docs/report.pdf", &mut out)?;
vault.lock();
```

- `Vault` — сессия; `!Sync`, `Send`; все операции `&mut self`.
- Никаких глобальных ключей; ключи живут в сессии.
- `Unlock` — enum: Password, Keyfile, Recovery, Fido2, Recipient.
- Ошибки — `SpError` с `code()` и `category()`.
- Публичные типы не реализуют `Debug`, если содержат секреты.
- SemVer; ломающие изменения — только major.

### 15.2. C ABI / FFI

- `sp_ffi` для GUI/мобильных/других языков.
- Функции: `sp_vault_open`, `sp_vault_close`, `sp_vault_put`, `sp_vault_get`, `sp_vault_list`, `sp_vault_delete`, `sp_vault_lock`.
- Ошибки — код + потокобезопасное сообщение; без секретов.
- Строки — UTF-8, владение явное; документировать.
- `cbindgen` для заголовка.
- Мобильные обёртки (UniFFI) — после v1.

### 15.3. Плагины

- В v1 нет плагинов: безопасность важнее расширяемости.
- В v2 — WASM-плагины с ограниченными правами (импорт/экспорт, UI-панели), без доступа к ключам.
- Плагины подписываются; реестр — позже.

## 16. Производительность

### 16.1. Цели

| Метрика | Цель |
|---|---|
| Разблокировка (Argon2 512 МиБ) | 0.8–2.5 с на референсном ПК |
| Пиковая RAM при разблокировке | ≤ 1.2 ГиБ |
| RAM в работе | ≤ 150 МиБ (без учёта кэшей ОС) |
| Последовательное чтение/запись на USB 3.0 | ≥ 80% от сырой скорости, цель 200 МБ/с |
| Последовательное чтение/запись на NVMe | ≥ 1 ГБ/с |
| Импорт 10 ГиБ | ≤ 60 с на USB 3.0 |
| Случайное чтение 4 КиБ (NVMe) | ≥ 5k IOPS |
| Старт CLI | ≤ 300 мс |
| Первый экран GUI | ≤ 1 с |
| 10 000 файлов: список/поиск | ≤ 2 с / ≤ 100 мс |
| Затирание | близко к сырой записи |

### 16.2. Как достигаем

- Параллельное шифрование чанков через `rayon` (по числу ядер, но с ограничением).
- Потоковые буферы 1–4 МиБ; без чтения файла целиком.
- `pread`/`pwrite` (или эквивалент) для random access.
- Кэш расшифрованных метаданных в памяти; чанки не кэшируются (или LRU с занулением).
- Отсутствие сжатия в balanced/paranoid; zstd только в compact.
- Избегать лишних копий: `Bytes`/`Vec<u8>` с переиспользованием буферов.
- `fsync` батчами, но не реже коммита.
- Бенчмарки `criterion`; сравнение с `dd`/`Copy-Item` на том же носителе.

### 16.3. Деградация

- На слабом CPU — light KDF, меньше потоков.
- На медленной флешке — прогресс и оценка времени.
- При нехватке RAM — отказ от paranoid KDF с понятным сообщением.
- При перегреве/троттлинге — не менять формат, только скорость.

## 17. Надёжность и восстановление

### 17.1. Гарантии

- Атомарный коммит: после `fsync` суперблока транзакция считается завершённой.
- При сбое — откат к последнему валидному суперблоку.
- Два заголовка и два суперблока.
- Проверка MAC/хешей при каждом открытии и чтении.
- Read-only при любой неопределённости.
- Никакого автоматического «ремонта» без бэкапа и подтверждения.

### 17.2. `sp doctor`

Проверяет:

- заголовки A/A′/B/B′;
- суперблоки A/B, generation, MAC;
- достижимость всех чанков;
- orphan-чанки;
- свободную карту;
- ссылки версий/снапшотов;
- размеры и границы;
- целостность индекса.

Действия:

- выбрать валидный суперблок;
- переписать повреждённый заголовок из резервного;
- освободить orphan-чанки (с подтверждением);
- пометить битые файлы как `damaged`, не удаляя;
- предложить экспорт уцелевшего.

### 17.3. `sp salvage`

Если индекс разрушен:

- сканировать чанки, пытаться расшифровать известными file key (если есть) или сообщить, что без индекса данные не восстановить;
- восстановить метаданные из старых суперблоков/снапшотов;
- экспортировать уцелевшее в папку;
- отчёт о потерях.

### 17.4. Бэкапы

- `sp backup` — копия контейнера на другой носитель; проверка BLAKE3.
- `sp export --plain` — опасный режим, только с предупреждением.
- Реплики в Paranoid — вторая копия после коммита; путь настраивается.
- Напоминание: бэкап контейнера бесполезен без пароля/recovery.

### 17.5. Конкурентный доступ

- Эксклюзивная блокировка на запись; shared на чтение.
- На сетевых ФС блокировки ненадёжны — предупреждение.
- Если том уже открыт другим процессом — `E_BUSY`.
- «Грязный» флаг после сбоя; `doctor` перед записью.

### 17.6. Нехватка места и обрыв

- Preflight-проверка свободного места.
- Резерв 64 МиБ.
- При обрыве питания — суперблок A/B.
- При извлечении носителя — I/O error, read-only, lock.
- При переполнении — отказ, без частичного коммита.

## 18. Безопасность разработки

### 18.1. Процесс

- Модель угроз и криптодизайн ревьюятся до кода.
- Любое изменение криптографии/формата — отдельный ADR + ревью двух человек.
- Запрещены «временные» обходы crypto и самодельные протоколы.
- Зависимости проходят `cargo audit`, `cargo deny`, `cargo vet`; новые — с обоснованием.
- Тест-векторы для всех примитивов; сверка с RFC.
- Фаззинг парсеров заголовков/метаданных/путей/журнала.
- Miri для core-крейтов; ASan/LSan на Linux CI.
- `cargo geiger` — контроль `unsafe`.
- Мутационное тестирование (`cargo-mutants`) для core — по возможности.

### 18.2. Секреты

- `secrecy::SecretBox` / `SecretVec`; `zeroize` при drop.
- `mlock` для мастер-ключа/ключей файлов; при неудаче — предупреждение.
- Запрет `Debug`/`Display` для секретов.
- Запрет логирования путей, имён, паролей, ключей.
- Запрет core dump (Unix) и best-effort на Windows.
- Очистка буфера обмена и превью при блокировке.
- Пароли не передаются в argv/URL/имени файла.
- Временные файлы — только с правами 0600 и затиранием.

### 18.3. Сборка

- `panic = "abort"` в release (GUI/CLI).
- LTO, `codegen-units = 1`, strip.
- `overflow-checks = true` в release для core (цена небольшая).
- `-C target-feature=+crt-static` для Linux CLI.
- Windows: Control Flow Guard, если доступно stable; иначе документировать.
- macOS: hardened runtime, notarization.
- SBOM (`cargo cyclonedx`), `cargo auditable`.
- Воспроизводимая сборка: фиксированный toolchain, `--locked`, remap путей, `SOURCE_DATE_EPOCH`.
- Проверка хешей двумя независимыми сборками.

### 18.4. Зависимости

- Только активно поддерживаемые crate-ы с внятной лицензией.
- Криптография — RustCrypto (`argon2`, `chacha20poly1305`, `hkdf`, `sha2`, `blake3`, `x25519-dalek`, `ed25519-dalek`, `subtle`, `zeroize`, `getrandom`).
- Shamir — `sharks` (или проверенная альтернатива).
- Tauri 2, Svelte 5, TypeScript — для GUI.
- `clap`, `serde`, `postcard`, `zstd`, `rayon`, `tracing`, `thiserror`, `rpassword`, `dialoguer`, `indicatif`, `fs2`, `tempfile`, `proptest`.
- Запрещены зависимости с телеметрией/сетью в core.
- Лицензии: MIT/Apache-2.0 совместимые; `cargo deny` блокирует GPL в core (если не решим иначе).

### 18.5. Раскрытие уязвимостей

- `SECURITY.md` с контактом, PGP-ключом, сроками.
- Приватное раскрытие через GitHub Security Advisories.
- 90 дней до публикации, по согласованию.
- Bug bounty — после v1.0, по возможности.
- Никаких бэкдоров, «универсальных паролей», скрытых ключей.
- Публикация advisories и CVE при необходимости.

## 19. Тестирование

### 19.1. Уровни

| Уровень | Что проверяем |
|---|---|
| Unit | крипто-обёртки, KDF, слоты, парсеры, пути, extents |
| Integration | создание/открытие/импорт/экспорт/удаление/восстановление |
| Property | round-trip, идемпотентность, границы, случайные последовательности |
| Fuzz | заголовки, слоты, метаданные, журнал, split, пути, recovery |
| Crash | kill -9 / power loss в случайных точках |
| Compatibility | контейнер, созданный на Windows, открывается на macOS/Linux |
| FS matrix | FAT32, exFAT, NTFS, APFS, ext4, read-only, network |
| Security | нет сети, нет plaintext на диске, tamper, rollback, side channels |
| Performance | throughput, latency, память, старт |
| Usability | 5 пользователей, сценарии без документации |
| Accessibility | клавиатура, screen reader, контраст |

### 19.2. Fuzz-цели

- `header_parse` — любые байты, без паник/переполнений.
- `slot_unwrap` — неверные пароли/ключи/типы.
- `metadata_decode` — повреждённые/огромные снапшоты.
- `path_normalize` — Unicode, `..`, NUL, длинные имена.
- `split_scan` — отсутствующие/лишние/битые части.
- `journal_replay` — обрывы, дубликаты, мусор.
- `shamir_combine` — неверные доли/порог.
- `recovery_parse` — BIP39/QR.

### 19.3. Крэш-тесты

- Fault injection на уровне `sp-storage`: ошибка/обрыв на каждом N-м вызове записи.
- Симуляция power loss через QEMU/`dm-flakey` на Linux.
- 100+ точек обрыва во время импорта 1 ГиБ.
- После каждого обрыва: `sp doctor`, проверка, что том открывается, последний коммит цел, открытого текста нет.

### 19.4. Матрица ФС/ОС

- Windows 11 + NTFS/exFAT/FAT32 (флешка).
- macOS 14 + APFS/exFAT.
- Ubuntu 24.04 + ext4/exFAT/FAT32.
- Read-only носитель.
- Почти полный носитель.
- Сетевой SMB (только предупреждение/чтение).
- Длинные пути Windows (>260) через `\\?\`.
- Unicode NFC/NFD, эмодзи, RTL-имена.
- 10 000 файлов, 1 файл 100 ГиБ (в пределах лимитов).

### 19.5. Безопасность

- Проверка отсутствия сетевых вызовов (`strace`/Wireshark/Proxyman).
- Поиск открытого текста на диске после операций (сканер временных папок/свопов).
- Проверка, что неверный пароль и повреждённый заголовок дают одинаковый ответ.
- Tamper: изменить байт в чанке/слоте/суперблоке → ошибка, без паники.
- Rollback: подменить контейнер старой копией → предупреждение (в рамках v1).
- Проверка, что скрытый том не перезаписывается внешним в protected mode.
- Проверка, что внешний read-only не пишет.
- Проверка zeroize (по возможности).

### 19.6. Покрытие и качество

- Цель: ≥ 80% строк в `sp-core`, `sp-crypto`, `sp-format`, `sp-fs`, `sp-vault`.
- `cargo llvm-cov` в CI.
- `clippy -D warnings`, `rustfmt --check`, `cargo doc` без warnings.
- Запрет `unwrap`/`expect` в библиотеках (кроме тестов); в бинарниках — с сообщением.
- Ошибки не должны содержать путей/секретов.

## 25. Юридические и этические аспекты

- Инструмент двойного назначения: защищает личные данные, но может использоваться неправомерно. В README — запрет на незаконное использование и ответственность пользователя.
- Криптоэкспорт: в некоторых юрисдикциях есть ограничения; код открытый, но пользователь отвечает за соблюдение местных законов. При необходимости — консультация.
- Лицензия: **MIT OR Apache-2.0** для кода; документация — CC-BY-4.0. Это разрешает коммерческое использование и аудит. Если нужна копилефт-защита — AGPL-3.0, но это отпугнёт часть корпоративных пользователей. Решение за заказчиком.
- Товарный знак: имя `SecretPiece` не зарегистрировано; при коммерциализации — проверить в своей юрисдикции.
- Приватность: приложение не собирает телеметрию, не требует аккаунта, не делает сетевых запросов (кроме opt-in обновлений).
- Ответственность: «как есть», без гарантий; предупреждение о риске потери данных и о том, что затирание на flash не гарантирует физическое уничтожение.
- Этическая позиция: не делать «wipe by duress» и не маскировать вредоносные функции. Duress-пароль только открывает декой-том.

## Приложение A. Почему не «настоящий скрытый раздел»

Идея «скрытый раздел на флешке» на практике означает одно из:

1. **Изменить MBR/GPT** — добавить раздел, который не виден в проводнике. Это ломает структуру носителя, требует прав, по-разному работает на разных ОС, легко обнаруживается и может привести к потере данных. Не делаем.
2. **Стеганография в свободном месте ФС** — писать данные в кластеры, помеченные как свободные. Это конфликтует с файловой системой, может быть затёрто, не кроссплатформенно и почти всегда обнаруживается. Не делаем в v1.
3. **Файл-контейнер** — обычный файл, внутри зашифрованный виртуальный диск. Не меняет структуру, работает везде, безопасен. Делаем.
4. **Скрытый том внутри файла-контейнера** — вторая область, не видимая внешнему тому. Даёт plausible deniability в разумных пределах. Делаем.

Таким образом, «скрытый раздел» в SecretPiece — это **скрытый том внутри обычного файла**, а не раздел диска. Это осознанное решение, а не упрощение.

## Приложение E. Глоссарий (кратко)

- **AEAD** — аутентифицированное шифрование с присоединёнными данными.
- **Argon2id** — memory-hard KDF, устойчив к GPU/ASIC.
- **COW** — copy-on-write, старые данные не перезаписываются до коммита.
- **Deniable** — правдоподобно отрицаемый; без пароля нельзя доказать наличие скрытого тома.
- **Extent** — непрерывный диапазон чанков, описывающий часть файла.
- **FS** — файловая система.
- **KDF** — key derivation function.
- **Nonce** — одноразовое число для AEAD.
- **Refcount** — счётчик ссылок на чанк/ключ.
- **Wear leveling** — выравнивание износа flash-памяти контроллером; причина, по которой перезапись не гарантирует физическое уничтожение.
- **Crypto-erase** — уничтожение ключей вместо перезаписи данных.
